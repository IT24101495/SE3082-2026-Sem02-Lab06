Exercise 4 - parallel for vs parallel for collapse(2)

Environment: Ubuntu 24.04 VM (VirtualBox), gcc 13.3.0, OMP_NUM_THREADS=4.
No qsub/cluster scheduler was available, so the programs were run directly.

  gcc -fopenmp exercise4.c  -o exercise4    (#pragma omp parallel for)
  gcc -fopenmp exercise4a.c -o exercise4a   (#pragma omp parallel for collapse(2))

Part 1 - #pragma omp parallel for  (4 threads)
Which thread ran which (r, k) iterations:
  thread 0 : r = 1 (k=1..10) and r = 2 (k=1..10)   -> 20 iterations
  thread 1 : r = 3 (k=1..10)                        -> 10 iterations
  thread 2 : r = 4 (k=1..10)                        -> 10 iterations
  thread 3 : r = 5 (k=1..10)                        -> 10 iterations
(Output appeared in order r=1..5, each block of 10 lines from a single thread.)

Part 2 - #pragma omp parallel for collapse(2)  (4 threads)
Which thread ran which (r, k) iterations (output lines were interleaved, so
they are grouped here by thread):
  thread 0 : r=1 k=1..10, r=2 k=1..3     -> 13 iterations
  thread 1 : r=2 k=4..10, r=3 k=1..6     -> 13 iterations
  thread 2 : r=3 k=7..10, r=4 k=1..8     -> 12 iterations
  thread 3 : r=4 k=9..10, r=5 k=1..10    -> 12 iterations

Explanation:
1. With `#pragma omp parallel for`, only the OUTER loop (r = 1..5, 5
   iterations) is divided among the threads. Each thread runs the complete
   inner k loop for the r values it receives. With 4 threads and static
   scheduling, thread 0 gets two r values (1 and 2) and threads 1-3 get one
   each, so the work is uneven (20/10/10/10) and at most 5 threads can ever be
   busy (with 8 threads, 3 would sit idle).

2. With `collapse(2)`, OpenMP merges the r and k loops into a single iteration
   space of 5 x 10 = 50 iterations and divides THAT among the threads. Each
   thread gets a contiguous chunk of about 12-13 iterations (13/13/12/12), so
   the load is nearly even, a single r value can be shared between threads
   (e.g. r=2 is split between threads 0 and 1), and more threads than 5 can
   be used effectively.
